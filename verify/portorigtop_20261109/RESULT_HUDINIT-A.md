## L-115 proofs (both are new classes: run the stand-in until L0 rules)

Instructions are from `original/MASHED.exe.unpatched` (capstone) and `match.py --show` on the recorded DDK
(13.00.9176 / 13.00.9178, `/O2 /Ob1 /G5`).

### 0x005c4ad0 (re/match/s28/005c4ad0.c, 96.7%, ops 100%, 61/61 instructions, 12 differing bytes)

Only one region differs, the second error report, `FUN_004d7ff0(0x80000013, count * size)`:

| original | DDK 9176 |
|---|---|
| 0x005c4b57 `8b 56 08` mov edx, dword ptr [esi + 8] | mov dword ptr [esp + 4], 1 |
| 0x005c4b5a `c7 44 24 04 01 00 00 00` mov dword ptr [esp + 4], 1 | mov edx, dword ptr [esi + 0xc] |
| 0x005c4b62 `0f af 56 0c` imul edx, dword ptr [esi + 0xc] | imul edx, dword ptr [esi + 8] |

The rest is byte-identical, relocations masked. Why they compute the same:
- Both read the same two dwords of the 0x10-byte header the function itself allocated and filled (+0x8 = 0x14, +0xc =
  param_1). Neither read can fault, alias or have a side effect.
- Two-operand `imul r32, m32` keeps the low 32 bits of the product, and that is commutative. edx ends the same.
- The flags `imul` sets (CF / OF) are not read before the next flag-setting instruction: the next three instructions
  are `push edx`, `push 0x80000013`, `call 0x004d7ff0`.
- The `[esp + 4] = 1` store moves across the load and touches neither esi's header nor edx.

So both write the same memory and reach the call with the same registers and the same stack. This runs only when the
second malloc fails.

Byte match tried in this step, none reached it:
- the swapped source order;
- casts on either operand;
- a struct view of the header;
- a comma rvalue;
- a hoisted product (82.0%).

The source header records 148 permuter compiles that did not move it either. Class: **commutative operand order of
one integer multiply**.

### 0x00555360 (re/match/s24/00555360.c, 94.4%, 89/90 instructions)

Two differing regions:

1. **The three failed-check returns.**
   - Original: 0x0055538d `75 01` jne 0x555390 / 0x0055538f `c3` ret, after `test eax, eax` on the 0x004cc9e0 result
     stored to 0x00912a08; 0x005553ba `75 01` / 0x005553bc `c3` after the 0x00912a14 store; 0x005553da `75 01` /
     0x005553dc `c3` after the malloc stored to 0x00912a0c.
   - DDK 9176: the first two are `je <shared>`, and the third falls into one shared `xor eax, eax / ret`.
   - On each of those paths eax = 0. The original returns the tested zero in eax, ours zeroes eax: the same value.
     esp, esi (not pushed yet at those points) and every store (the global is written before the test in both) are
     the same, and nothing else runs between the test and the `ret`.
2. **One store pair in the index loop.**
   - Original: 0x00555467 `66 89 70 fe` mov word ptr [eax - 2], si before 0x0055546b `66 89 08` mov word ptr [eax], cx.
   - DDK 9176: the [eax] store first, then the [eax - 2] store.
   - The two stores write the 2-byte slots eax - 2 and eax, which do not overlap. The loop holds no read of memory
     between them. si and cx are not changed between them. So the memory after the pair is the same.

The source header records the byte-match attempts already made: return-the-tested-global, a result variable,
else-chains, a pointer return type, game flags, a 60-order store sweep and 260 permuter compiles. Classes:
**return-block layout with an equal eax** and **order of two stores to non-overlapping addresses**.
