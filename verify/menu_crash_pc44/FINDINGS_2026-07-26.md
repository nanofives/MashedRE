            0x004669fb 0x004028e0 0x004923d5 0x004a4d38 0x00400000 0x004a4bb7 0x004a4bcf

`eip=0x00000044` with `ebp=0` = a call through a **near-null function pointer** (field at +0x44 of a
null/garbage object). The return chain is dominated by the **CRT band** (`0x004a4bb7` = `entry`,
`0x004a4bcf`, `0x004a4d38`, `0x004a4d60`, `0x004ac660`, `0x004abbe5`) → the fault happens during
**CRT startup / static-init**, before the game's own main loop. This matches the
`project_boot_crash_static_init_not_heap` class, not the menu/RW-asset framing.

## Corrected observation about exit codes (this misled the first hour)

`Start-Process -PassThru` reports `ExitCode = -1` (0xFFFFFFFF) for this crash, which CLAUDE.md's
multi-session note describes as the *force-kill* signature. Using `WaitForExit()` before reading
`ExitCode` yields the true **`-1073741819` = 0xC0000005**. Anyone triaging a boot failure must
`WaitForExit` first, or they will misclassify an AV as a clean exit and follow the wrong branch of
the decision tree (as happened here).

# CORRECTION (same day, later) — THE `.asi` IS THE TRIGGER. Everything above the line is WRONG on attribution.

The "ruled out: our `.asi`" row in the table above is **invalid**, and so is the "system-level DLL /
CRT-init" hypothesis. Two measurement errors produced it. Corrected, reproducible A/B — 3 runs per
arm, every run measured with `WaitForExit()` before reading `ExitCode`:

| configuration | result |
|---|---|
| stock: `dinput8.dll` **and** `d3d9.dll` both parked | **ALIVE 22 s** ×3 |
| `d3d9.dll` shim only (dinput8 parked → no `.asi` loaded) | **ALIVE 20 s** ×2 → the d3d9 shim is INNOCENT |
| **both** `.asi` copies parked, loader + shim present | **ALIVE 20 s** ×2 |
| **`MASHED_RE_NO_AUTO_HOOK=1`** (documented guard, no file moves) | **ALIVE 20 s** |
| `.asi` loaded via dinput8 auto-load | **AV 0xC0000005 @ 4.6 / 4.8 / 5.1 / 5.6 / 6.1 s** |

This **restores** the 2026-07-25 finding (`project_menu_crash_vfs_dir_truncation`): it is our `.asi`.
Timeline for the one defect: **~94 s (05-30) → ~10 s (07-25) → ~5 s (07-26).**

## The two errors, so nobody repeats them

1. **`LoadDevAsi()` in `mashedmod/src/dinput8_shim/dinput8_shim.cpp` has a FALLBACK.** If
   `original\mashed_re_dev.asi` is missing it loads `..\mashedmod\build\mashed_re_dev.asi`
   (lines ~56-71). Renaming only the deployed copy therefore does **not** unload the hooks — the
   build copy loads instead, and you measure a hooked process while believing it is stock. That is
   exactly how the first "not our code" conclusion was reached. **Park BOTH copies, or set
   `MASHED_RE_NO_AUTO_HOOK=1`.**
2. **`Start-Process -PassThru` with `HasExited` polling reports `ExitCode = -1` (0xFFFFFFFF)** for
   this AV. CLAUDE.md documents 0xFFFFFFFF as the *force-kill* signature, so it reads as a clean
   exit — which is what sent this investigation down the AppCompat/HKLM/reboot branch and produced
   the (real, but irrelevant) finding that compat layers are not involved. **Always `WaitForExit()`
   before reading `ExitCode`.** True code: `-1073741819` = 0xC0000005.

## What this explains about the whole session

The AV fires ~5 s after the `.asi` loads; a single-hook `run_diff` completes in **~4.2 s**. The six
C2→C3 promotions banked earlier today were **winning that race by roughly half a second**. When a
later batch's diffs needed slightly more setup they crossed the threshold and failed at
`frida.attach` with `VirtualAllocEx returned 0x00000005` — which is Frida attaching to a
already-dying process, a symptom rather than the disease. **Any `run_diff` GREEN obtained while this
defect stands is a race win, not evidence of a healthy harness.** The six promotions' *bit-identity*
evidence is still valid (the diffs did complete, with real per-case fingerprints), but the harness
they ran on is not sound and should not be trusted for further promotion until this is fixed.

## Still valid from the dump

`eip=0x00000044`, `ebp=0` → call through a `+0x44` field of a NULL object; ret-chain is CRT-band
(`0x004a4bb7`=`entry`, `0x004a4bcf`, `0x004a4d38`, `0x004a4d60`, `0x004ac660`, `0x004abbe5`), so the
fault is in static-init / load-time work — consistent with the trigger being `.asi` **load** rather
than hook installation, and with the 07-25 observation that `MASHED_HOOK_ONLY` subset installs never
dodged it. The "no WER dump" claim was also an artefact: `%LOCALAPPDATA%\CrashDumps` was at its
10-dump retention cap; archive it and a dump appears on the next run.

Genuinely ruled out (and still useful): AppCompat layers HKCU **and** HKLM (tested via
`__COMPAT_LAYER` and via a renamed copy, since layers are path-keyed), `EMULATEHEAP`, the PCA store,
binary drift (`MASHED.exe` SHA-256 `1110BFB5…` byte-identical throughout), the nine boot patches,
`videocfg.bin`, a full reboot, and the d3d9 shim.
