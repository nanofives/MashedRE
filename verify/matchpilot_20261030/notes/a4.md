Observations on 13.00.9176/9178 vs 13.00.9466:
- 3 of 4 functions reach every compared instruction, frame/allocation/scheduling included. Each gap that did close came from source shape: hoisted loads (00483ca0, 00478cf0), an element pointer for the induction base (00478cf0), split statements (004783f0). For 00478cf0, the order of one load against one test decided register allocation for the whole 827-byte function (`t` in ebp vs reloaded from the stack), and the original form fixed it everywhere.
- The only (a) candidate is a list-scheduling order in 004783f0, block 0x00478464..0x004784e9. The original issues one `fld [eax+ebx+0xc1cc]` and then `lea esi / lea eax / push ecx` before the remaining FP ops. 9176 issues all 6 FP ops first on [reg+ebx+disp] and the leas after. 6 source reshapes, /G6 /G7 /GB and 2 permuter runs (580 compiles) did not reproduce it. Moving an unrelated store into the block does reorder it, so the scheduler is sensitive to block content. That makes this weak evidence, not proof, of a 9466 difference.
- 9176 refactors `x + a*0.0f + b*0.0f` into `(a+b)*0.0f + x` (an algebraic float transform under /O2). The original keeps the left-to-right order. Splitting the sum into two statements matches, so source shape explains it (plausible original source) and it is not evidence by itself. It is worth checking whether 9466 applies the same transform.
- `acos` in the game is the CRT stack-arg entry 0x004a3384, not the /Oi `_CIacos` register form that 9176 emits for a `double acos(double)` prototype. Declaring it as a plain function under another name matches. Header or pragma context in the game source, not compiler version.
- Tool limit (c), in 2 of 4 functions: the `re/console/pc_funcs.csv` sizes (482, 824) stop short of the real ends (0x004785da, 0x0047902a). This undercounts both scores. `match.py` should cap at the next function entry or `ret` instead of at the table size.
- No `in_*`/`unaff_*` register inputs and no non-standard conventions in these 4 (all cdecl), so no /GL signal.
