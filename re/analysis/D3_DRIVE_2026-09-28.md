### 1.4 The bisect route

**Step A — the control that has to run first.** Build `56ad3806` and measure it
**today**. If today's `56ad3806` does not reproduce `1887` / `0.1916`, the drift is
environmental (toolchain, assets, machine state) and not a commit at all, and the
whole bisect is void. This control is not optional and its result is reported either
way.

**Step B — informed probe, then binary search.** Probe #3 `647a5e24` (the last commit
before the AI port) and then #4 `09a73dc6`. If #3 is GOOD and #4 is BAD, the first bad
commit is #4 in two builds. Any other outcome falls back to plain binary search over
the surviving interval (#1..#3 or #5..#17), worst case 5 further builds.

**Step C — the exact change.** A first-bad commit is not an answer. The commit is then
reduced to the specific hunk by reverting hunks one at a time on top of HEAD and
re-measuring, and the mechanism is cited to an RVA before any fix is written.

### 1.5 How each commit is built — no worktrees

Per the session rules, worktrees are created only via the `worktree` skill and removed
only via `py -3.12 scripts/diag.py wt-remove`. This bisect avoids them entirely:

```
git checkout <commit> -- mashedmod/          # tracked build inputs only
mashedmod\build.bat                          # per-TU object cache recompiles the delta
py -3.12 re/tools/statediff/a8_run_port.py verify/d3_drive_20260928/b_<commit> 50 -MASHED_REAL_PHYSICS
git checkout HEAD -- mashedmod/ && git status --short   # restore, and prove it
```

`mashedmod/exe_sources.rsp` changed inside the range (four of the powerup commits add
TUs), so `mashedmod/` is checked out as a unit rather than `mashedmod/src` alone —
otherwise the HEAD source list would name files the old tree does not have. Files that
exist at HEAD and not at the probed commit stay on disk but are absent from that
commit's `exe_sources.rsp`, so they are not compiled. `re/` and `verify/` stay at HEAD
throughout, so every probe is reduced by the same tooling. **`original/` is never
touched.** Only PIDs spawned by `a8_run_port.py` are killed, by that script, by PID.

## 2. Criterion (e)'s tolerance — measured and fixed BEFORE any post-fix capture

### 2.1 The recipe and the window


Window, per car `v`: the first **220** calls starting at the first call with `c4 != 0`.
This is `re/tools/ai_ctrl_window.py`'s window, unchanged — criterion (b) is scored on
the same span, so (b) and (e) cannot disagree about which calls are the race.

### 2.2 The three statistics, defined before they were computed on any port capture

Implemented in `re/tools/ai_speed_env.py`, which is the only scorer for (e).

| stat | definition | gated |
|---|---|---|
| `launch` | `rec_9e4` at window index 11 minus `rec_9e4` at window index 0 | **yes** |
| `ft_median_m0` | median `rec_9e4` over window calls `[0, k)` with `c4 == 255` and `c5 == 0`, where `k` is the index of the **original's** first `ai_mode != 0` call | **yes** |
| `ft_median` | the same median over the whole 220-call window | no — reported |

`rec_9e4` is `|velocity|` over all three axes (`Integrate2.cpp:119`,
`Wf(v, 0x9e4, Vec3Mag3(v+0x9b0))`).

**Why `ft_median_m0` is the gated median and the full-window `ft_median` is not.**
The full-window median is the statistic §2.1 control B of the speed-gap note reports
(+25.5 / +6.8 / +5.2%), and it is kept for continuity — but it is **not a physics-only
comparison while residue D3-R1 is open**. `k` is measured at **100 / 23 / 39** for cars
1 / 2 / 3, identical on all 10 regime-0 original captures. Past `k` the original's
speed history has run through behaviour modes 3 and 7, which the standalone cannot
have because `FUN_00414c30` / `FUN_00484c70` are unported (that is D3-R1 itself).
Mode 7 sets `ctrl[4] = 0x40` at `0x0041688d`; mode 3's calls carry the original's
`c4 = 0, c5 = 255` braking. So beyond `k` the two sides are running different inputs
by construction, and a median taken there scores the missing modes, not the drive
model. Within `[0, k)` the original is in mode 0 on every call, which is the only span
on which "same ctrl bytes, compare the speed" is a statement about physics. For car 1
`[0, 100)` is exactly the 97-call matched span of §2.1 control A.

This is a scoping decision, not a weakening one: the current gap on `ft_median_m0` is
**larger** than on the full-window median (see §2.4).

### 2.5 The regime condition, and why two of today's four captures are excluded

`flag_a368` is the AI step dump's copy of `DAT_0089a368`, whose `== 1` arm multiplies
`ctrl[4]` by 0.4 at `0x004169e0`. On this recipe it is **not** binary: the twelve
captures show values 0, 1 and 2. The reference regime is **`flag_a368 == 0` on every
call of the window**, which is the regime of the eight committed non-flip originals and
of every standalone capture taken so far (`sa_d1`, `sa_d2`: 0 on 220/220 window calls
on all three cars). `e1` (value 1 on 159 of 220) and `e2` (value 2) are outside it and
are excluded from the envelope — committed as evidence, not deleted.

Worth recording because it bears on how robust the gate is: even in the off-regime
runs, `launch` is **1425.7 / 2052.5 / 2055.0** — identical to the reference — and
`ft_median_m0` is identical on cars 2 and 3. Only car 1's `ft_median_m0` moves
(2043.0 on `e1`), because the flag arrives before its `k = 100`. So a port capture that
lands off-regime invalidates car 1's median and nothing else; `--check` prints
`regime0` per car and a post-fix capture with `regime0=0` on car 1 is re-taken rather
than scored.

## 3. MEASURED — the drift bisect, and what it actually is

**Verdict up front: the drift is NOT a change to the ported drive laws.** The first bad
commit is `09a73dc6`, and the mechanism is that the `a8` held-lock recipe stopped being a
controlled instrument, not that the player's physics stopped being faithful. Three of the
four candidate mechanisms were tested and refuted by measurement. A residual is left
unexplained and marked `[UNCERTAIN]` in §3.6 rather than papered over.

Every number below is `slip vs fwd` in the 1500-2000 band, from the §1.3 recipe, with the
driving-median speed and the logged frame count alongside. GOOD reference = the D2 table's
`0.1916` / `1887`.

### 3.1 Step A — the control, and the premise it refuted

Today's build of `56ad3806` reproduces the D2 gate table, **4 runs out of 4**:

| run | lines | slip 1500-2000 | slip 2000-2600 | av.y | driving-median |
|---|---:|---:|---:|---:|---:|
| `g56_1` | 1083 | 0.1916 | 0.2669 | 1.123 / 1.591 | 1928.48 |
| `g56_2` | 1084 | 0.1916 | - | 1.120 | 1914.91 |
| `g56_3` | 1083 | 0.1916 | - | 1.123 | 1931.36 |
| `g56_4` | 1084 | 0.1916 | - | 1.123 | 1928.48 |

D2's row was slip `0.1916` / `0.2668`, av.y `1.12`/`1.59`, median `1887`. **So the drift is
a commit, not environmental**, and the bisect is valid.

It also establishes that the GOOD endpoint is *stable*: four runs agree to four decimals on
slip even though the logs are byte-divergent from frame 58 onward (`g56_2` shares only 58
lines with `g56_1`). That stability is what HEAD has lost.

### 3.2 The §1.3 one-run-decides premise is REFUTED, and this is how

`09a73dc6` produced **both** verdicts from one build:

|---|---:|---:|---:|
| `b_09a73dc6` | 1623 | 0.1840 | 2154.33 |

here rather than quietly widened, per the §2.4 lesson.

The 0.1283 attractor is reachable at `09a73dc6` and at HEAD and **not** at `647a5e24` or
`56ad3806`. That is the bisect signal that survives.

### 3.4 What in `09a73dc6` - three mechanisms tested, three refuted

`09a73dc6`'s diff over `mashedmod/` touches the player's own code path **nowhere**. Its
`TrackRenderer.cpp` hunks all sit at or after `@@ -2839` (the opponent block inside
`UpdateCar`, and the extraction of `AiOptionBStep`); its `VehiclePhysicsRun` diff adds
`raw_steer` (defaults 0, and the player's `io` never sets it) plus the read-only accessor
`VehiclePhysics_RecordF32`; its `exe_main.cpp` hunk adds `InitPickups()` inside the
`MASHED_ROUND` branch, which this recipe does not set. So the only routes to the player are
the opponents and the AI-tick globals. Each was A/B'd at HEAD with temporary env-gated
diags (`MASHED_D3_NOOPP`, `MASHED_D3_NOAIPHYS`, `MASHED_D3_NOTICK`, `MASHED_D3_CPOINTS`),
removed afterwards:

| configuration | slip 1500-2000, 3 runs | lines | reseed-excluded rows |
|---|---|---:|---:|
| HEAD, as shipped | 0.1283 | 1624 | 0 |
| HEAD `NOOPP=1` (opponents not updated at all) | **0.1427, 0.1427, 0.1427** | 1443/1442/1442 | 0 |
| HEAD `NOOPP=1 NOTICK=1` (also no AI tick/clock) | 0.1717, 0.1427, 0.1427 | 1624/1443/1443 | 0 |

| HEAD `NOAIPHYS=1 NOTICK=1` (opponents on the pre-`09a73dc6` kinematic step) | 0.1736, 0.1561, 0.1774 | 1246/1246/1249 | 0/64/64 |
| HEAD `GATE_RIBBON_AI=1` | 0.1774, 0.1612, 0.1757 | 1443/361/1443 | 0 |

Read off it:

1. **REFUTED - `f39747af`'s `Collision::Rw_TransformPoints` rebind.** This was the second
   named suspect of §1.2, and the one U-9138 explicitly left unproven ("nothing has proved
   the Collision copy inert"). Restoring the pre-`f39747af` POINTS binding at HEAD gives
   `0.1427` on the run that matches the `NOOPP` control frame-for-frame, i.e. **no change**.
   The flip is inert on this recipe too.
2. **REFUTED - the AI tick itself.** `NOTICK` on top of `NOOPP` changes nothing (`0.1427`
   twice, one outlier at a different frame count). The clock advance
   (`0x0040fc63`/`0x0040fe5e`), `AiBridgeSnapshot`, `Ai_Standalone_Tick` and `AiStepDump`
   do not move the player. The standalone's output-slot table is explicitly written
   `v -> v` (`TrackRenderer.cpp:155`, `0x007f1a14 + v*0x10`, the offset cited at
   `AiState.h:41` from `0x0041856c`), so the opponents never write the player's ctrl block
   0 - which is the mechanism this test was aimed at.
3. **CONFIRMED as the variance source - the opponents.** With the opponents not updated,
   HEAD is **stable to four decimals on 3/3 runs** (`0.1427`), and `09a73dc6` gives the
   identical `0.1427` on 3/3. With them updated, HEAD spans 0.128..0.177. So `09a73dc6`'s
   real effect on this recipe is that three RNG-driven physics bodies now share the
   player's world during a 50 s full-lock donut taken at the start line. The original has
   opponents too - this is the port becoming *more* faithful - but the consequence is that
   the recipe's aggregate is no longer a measurement of the drive laws.

### 3.5 At least one later commit moves it too - the race got longer

The logged frame count is deterministic per configuration and is not constant across the
range: 1083 at `56ad3806`, 1623 at `09a73dc6`, 1246 with the opponents put back on the
kinematic step at HEAD. The recipe is wall-clock-bounded at 50 s and every run counted here
ended on its own (`exe exited on its own rc 0`), so the count is the race's length in
frames. `4ff428ad` is the commit that made the match target derive from the rule engine
(G-G1) and turned `rule_engine_on_` on (G-G2), which is a race-length change by
construction. A longer race repopulates the reducer's speed bands, and the bands are what
the D2 table is made of. Recorded as a second, independent way the D2 numbers moved with no
drive law changing.

### 3.6 [UNCERTAIN] U-D3-DRIFT-RESIDUAL - what is NOT explained

Putting the opponents back on the pre-`09a73dc6` kinematic step at HEAD recovers most of
the GOOD signature: `slip 2000-2600` returns to **0.2720 / 0.2751 / 0.2812** against D2's
`0.2668` (HEAD as shipped: 0.2950), and the 64-row reseed exclusion that is present in all
four `56ad3806` runs and absent at HEAD **comes back on 2 of 3 runs**. But

## 4. MEASURED — U-D3-DRIVE: one defect found and fixed, criterion (e) still FAILS

### 4.1 The gearbox suspect of §6.3 — right site, wrong cause, and the real cause

`D3_SPEED_GAP_2026-09-28.md` §6.3 named the gearbox pair `+0x490`/`+0x494` as the first
place to look. It is the right site. It is **not** the cause, and the constants are **not**
the cause either:

| field | original (`e3.msd`, read at runtime) | port (read at runtime) |
|---|---|---|
| `+0x498` | 40000 | 40000 (`VehicleInit.cpp:79`) |
| `+0x49c` | 4000 | 4000 (`VehicleInit.cpp:78`) |
| `+0x478..+0x48c` | — | 4.00 / 3.00 / 2.40 / 2.10 / 1.80 / 6.00 |

The cause is the gearbox's **input**. Read out of the original's own capture
(`verify/d3_drive_20260928/e3.msd`, frames 854-859, at rest on the grid immediately before
the race, via the new `re/tools/statediff/msd_fields.py`):

```
+0x9b4 (vy) = 0.000   +0x9e4 (speed) = 0.000   +0xb0c = 0.0000
loads (+0x210/+0x2d4/+0x398/+0x45c) = 1083.3 / 1083.3 / 1083.3 / 541.7
+0x490 (gear) = 0     +0x494 (shift timer) = 0
wheel states (+0x168/+0x22c/+0x2f0/+0x3b4) = 2 / 2 / 1 / 1
```

The port's first step ran with those loads at **zero** (`VehiclePhysics_Init` memsets the
record), so gravity was unopposed for exactly one step and the body picked up **216.67 of
downward velocity** — measured on the player and on all three AI slots alike. Because that
velocity is almost entirely vertical, A4's slide measure at `VehicleControl.cpp:113`
(`(1 - |fwd . vel| / speed) * speed`, at-rest zero arm `:106` / `0x0047072c`) read
**216.668** instead of ~0. `Integrate2.cpp:126` (`FUN_00467650`) then shortened
`fVar5_base` to `1500 - 216.668`, dropping `fVar5` from 2000 to 1711, so the gear-0
candidate `(speed + 250) * 4 = 1862` **exceeded** it and the upshift test at `:136-143`
fired. The port left gear 0 on its second step (`gear=1 gtmr=2950`, measured), and gear 0
is the only gear with a nonzero drive term at standstill (`:134`,
`t = (speed + 250) * [+0x478]`; every other gear is `g * speed = 0`).

**The fix is the spawn settle** (`VehiclePhysicsRun.cpp`, `VehiclePhysics_StepCar`): one
step with an all-zero input block, which is what establishes the loads — measured, they
reach `1083.34 / 1083.34 / 1083.34 / 541.671` after exactly one step, matching the
original's `1083.3 / 541.7` — then discard the velocity that step injected and reset the
gearbox pair. No position moves: `StepCar` returns motion through `io.drive_delta` and the
settle call discards it. Cleared per slot by `VehiclePhysics_Init`.

Measured after the fix, first real step, player and all three AI slots: `gear 0`, `gtmr 0`,
`b0c 0`, loads `1083.34 / 1083.34 / 1083.34 / 541.671` — the original's row. `b0c` stays at
1e-6 through the launch where it used to run 216 -> 19 over seven frames, and gear now
holds 0 until the speed threshold, as the original's does.

The upshift **law** is confirmed faithful on both sides once the input is right: the
original is still gear 0 at recorded speed 370.5 and shifts at 558.5, which is the test
reading the **entry** speed (`(180+250)*4 = 1720 < 2000`, then `(370.5+250)*4 = 2482 >
2000`). The port now shifts at entry speed 266.8, i.e. the same law reached at a lower
speed because its ramp is still short (§4.4).

### 4.4 [UNCERTAIN] U-D3-DRIVE-FORCE — what is left, localised but not decoded

After the settle the port's speed gain per frame at the launch is still roughly an order of
magnitude short: 13.3 / 13.6 / 14.4 / 15.2 per frame over its first four real steps, where
the original's are 180 / 190 / 188 / 198. The gear is now right on both sides, the input
bytes are `c4 = 255` on both, all four wheels are in contact on both, the wheel states are
`2/2/1/1` on both, and the gearbox constants match. So the remaining defect is in how
`local_cc` becomes force, not in the gear selection.

Localised to the drive accumulator `+0xb14`/`+0xb1c`, at matched speed:

| | speed | `+0xb1c` (drive Z) |
|---|---:|---:|
| original `e3.msd` frame 861 | 370.5 | -1.14331e+07 |
| original `e3.msd` frame 860 | 180.0 | -1.08e+07 |
| port `gb2` step 10 | 168.5 | +1.31726e+06 |
| port `gb2` step 20 | 369.3 | +1.22926e+06 |

i.e. the original's magnitude is **8-9x** the port's at the same speed, and the port's own
value matches the formula the port implements: at speed 168.5, `local_cc = 2.5 * (168.5 +
250) * 4 = 4185`, `drive = min(160, 255) * local_cc = 669568`, accumulated over the two
state-2 wheels with forward-axis Z `0.9998` gives 1.339e6 against the 1.317e6 logged
(`Integrate2.cpp:216-234`).

**This 8-9x is NOT established as the defect, and no fix is offered for it.** The reason is
already on record in this repo: the `[A8-B14CADENCE]` comment at
`VehiclePhysicsRun.cpp:849-855` warns that a render-tick snapshot of `+0xb14` may be a
**residue after the whole substep loop**, not the force the integrator consumed, in which
case every figure derived from the captured `+0xb14` — including the table above — is
invalid. A4 zeroes `+0xb14` at entry (`VehicleControl.cpp:102`), so the original's snapshot
is an end-of-frame value while the port's log line is taken after one A6a pass. The two are
not obviously like-for-like, and a factor near 8 is exactly what a per-substep accumulation
would look like.
