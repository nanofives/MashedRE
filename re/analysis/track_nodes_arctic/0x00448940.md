## Purpose (C3 prose)

Bring the **arctic** course up. Reset the render-state globals, run the three
sibling arctic helpers, detach the course's clump[2] from the world frame and
replicate it 24 times into a 25-entry tile array, translate the 25 tiles into a
5x5 grid 60 units apart at Y = -4.1, register a `"smoke"` particle emitter,
instantiate the course's three object lists into the handle array under a shared
cursor, append one more object at a fixed position, and — only when the course's
`+0x105f8` and `+0x105fc` floats compare **equal** — push two camera values and a
triple.

It is **not reachable by a direct call anywhere in `.text`**. It is reached only
through the per-track node table, which is why Ghidra lists zero callers and why
the function was not even defined in Ghidra before this effort
(`decomp_pc.py --create` inside a `-readOnly` run).

### The grid

```
0x00448a65  mov [esp+0x10],0xc3160000   ; X start = -150.0
0x00448a6d  xor edi,edi                 ; k = 0, the SAME counter that indexes tiles[]
0x00448a6f  mov ebp,5                   ; outer = X
0x00448a80  mov [esp+0x18],0xc3160000   ; Z start = -150.0, reset per outer step
0x00448a88  mov ebx,5                   ; inner = Z
0x00448a90  mov ecx,[edi*4 + 0x8963e0]
0x00448aa2  call 0x4c1340(frame, &v, 0) ; combine op 0 = rwCOMBINEREPLACE
0x00448aab  fadd [0x005cc728]           ; Z += 60.0
0x00448ac1  fadd [0x005cc728]           ; X += 60.0
```

=> 25 tiles, X and Z each in {-150, -90, -30, 30, 90}, Y = -4.0999999 on all 25.
The coordinates are ACCUMULATED, not multiplied. -150, -90, -30, 30 and 90 are
each exactly representable in binary32 and 60.0 is exact, so repeated addition
and `-150 + 60*i` agree bit-for-bit here; the port still accumulates.

### The three object loops

Each count is read with `test eax,eax` + `jle`, so it is **SIGNED** and `<= 0`
skips the loop entirely.

| count | base | stride | type |

| `course+0x10008` | `course+0x2030` | 0x40 | `7` |
| `course+0x1000c` | `course+0x3030` | 0x40 | `2` |

Each result goes to `[0x008962e0 + [0x0068324c]*4]` and bumps `[0x0068324c]`.

## TWO GHIDRA ARITIES ARE WRONG

Ghidra prints `FUN_004671a0(0,0x44480000)` and `FUN_004c1b10(uVar1)`. Both are off
by one argument, and porting the decompiler's version would have pushed 800.0f
into the wrong callee. The call site cleans all 8 pushes at once (`add esp,4` at
`0x00448c7d` plus `add esp,0x1c` at `0x00448ca9` = 32 bytes), which is what let
the decompiler mis-attribute a slot:

```
0x004671a0  call 0x42b930 / cmp eax,3 / cmp dword ptr [esp+4],-1   -> ONE argument
0x004c1b10  fld [esp+8] / mov esi,[esp+8] / fstp [esi+0x84]        -> TWO
```

So the real calls are `FUN_004671a0(0)` and `FUN_004c1b10(raster, 800.0f)`.

## Uncertainties

- [UNCERTAIN U-9163] the semantics of every course-object field read here are NOT
  established and are recorded as cited offsets only: `+0x10004`, `+0x10008`,
  `+0x1000c` (three signed counts), `+0x1030`, `+0x2030`, `+0x3030` (their record
  bases, stride 0x40), `+0x10118` (the clump the tiles are cloned from),
  `+0x105d4` (the frame it is detached from), `+0x105f8` / `+0x105fc` (two floats
  compared with FCOMP).
- [UNCERTAIN U-9164] `0x008962c0..0x008962cc` is a 4-dword copy of `bb[+0x1c..+0x28]`
  where `bb = FUN_004b3f90(clump)`. What the four dwords mean is not established.
- [UNCERTAIN U-9165] `0x008962e0` (the handle array), `0x0068324c` (its cursor) and
  `0x00683248` (the cursor snapshot taken before the extra object) are named
  mechanically. Their consumers are not traced here.
- [UNCERTAIN U-9166] `FUN_00496d00` is passed `0x0049a0c0`, a CODE address, i.e. a
  callback. The callback itself is not analysed here.
- [UNCERTAIN U-9167] the tail branch runs ONLY when `course+0x105f8 == course+0x105fc`.
  Whether that condition is ever true on shipping arctic data was NOT measured;
  the canonical run above cannot distinguish "ran and matched" from "both arms
  skipped it", so the tail is covered by the port but NOT by the evidence.
