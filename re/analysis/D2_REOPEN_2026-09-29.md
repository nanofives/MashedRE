## 3. THE PASS RULE (pre-registered)

### 3a. Per-metric bound

For each of the three metrics, the port's scored solo value must satisfy

> `|port - mean_orig|  <=  tol`,   `tol = max( 3h , 2% of mean_orig )`

`3h` covers the whole observed original-side spread with margin. The 2% floor is the tolerance
this project already uses for D2-class comparisons (`re/analysis/U9138_FIX_2026-09-28.md` §5
driving-median "within 2%"; `re/tools/ai_speed_env.py:115` `BAND_PCT = 2.0`) and stops the
`2000-2600` band — where the original happens to be almost perfectly repeatable — from being
given an absurdly tight 0.18% band.

| metric | mean_orig | 3h | 2% of mean | **tol (the larger)** | **PASS interval** |
|---|---:|---:|---:|---:|---|
| slip 1500-2000 | 0.19245 | 0.00390 | 0.00385 | **±0.00390** | **0.18855 .. 0.19635** |
| slip 2000-2600 | 0.249875 | 0.00045 | 0.00500 | **±0.00500** | **0.24488 .. 0.25487** |
| driving-median | 1943.57 | 30.02 | 38.87 | **±38.87** | **1904.70 .. 1982.44** |

### 3b. Port-side determinism precondition

U-9148 records that one HEAD solo run in five lands in a second attractor
(`1818.47` vs `1505.12` driving-median). So a single port run may not be scored.

> Take **at least 3** port solo runs. At least 3 of them must agree with each other within the
> ORIGINAL's own half-range `h` on every metric (±0.0013, ±0.00015, ±10.005). The agreed value
> is the scored value. Every non-agreeing run is reported with its numbers. If no 3 runs agree,
> the arm **FAILS on determinism** regardless of where the numbers land — an arm that cannot
> reproduce itself cannot be compared to a deterministic reference.

### 3c. Verdict

D2 re-closes only if **all three** metrics fall inside their §3a interval **and** §3b is
satisfied. Two-of-three is a FAIL, and is reported as a FAIL.

### 3d. What is NOT a gate here (reported, not scored)

Per the session directive, and to keep this rule from being gamed:

- criterion (e) (`re/tools/ai_speed_env.py --check`), AI criterion (b)
  (`re/tools/ai_ctrl_window.py --check`), the power-up sweep
  (`re/tools/pu_replay/sweep.ps1`) and the modes oracle are **regression guards**. They are run
  after each fix and **reported as-is**. If a fix that is faithful to the original moves one of
  them, that is stated plainly and the fix is kept — the guards are not tuned back.
- The ONE hard non-metric gate is the build: `mashedmod\build.bat` must complete with the
  dual-copy guard reporting **`NEW=0`** (`scripts/lint_rva_bodies.py:120-122`). No fix may
  introduce a new duplicate body.

**Answer: `[esp+0x3c]` is `E+0x0c`, A4's `param_3` STACK SLOT, which A4 reuses as a
local at `0x004706a2` to hold `record + [record+0x9a8]*0x40 + 0x928`.** A6b's ESI is
therefore *literally the same pointer* A5 gets as its second argument
(`0x00470918`) and A6a as its third (`0x00470928`). Reading the slot as
"param_3/input" or as "param_4/xform" both mis-identify it, which is how the tree
came to hold two different wrong answers at once.

**The frame is fully accounted for.** U-9149 recorded "`add esp, 0x24` does not
balance A6a's four pushes plus A6b's two, so there is a `sub esp` or further pushes
unaccounted for." There is neither: the `0x24` cleans **A5's three** as well
(3+4+2 = 9 dwords = 0x24), and the five prologue pushes are undone by the five
epilogue pops. `push ecx` at `0x00470670` is the MSVC 4-byte-local idiom, used at
`0x004707b7`/`0x004707bb` for the `fild` int->float staging. **U-9149's missing
evidence is closed.**

### 4.2 The object is an RwMatrix

From A6b (`py -3.12 re/tools/disasm_fn.py 0x00468980 0x00468b40`, `RET`s at
`0x00468aba` / `0x00468b34`):

- `0x00468a31`, `0x00468aaf`, `0x00468b29` all `call 0x4c4d20` = `RwMatrixRotate`,
  with `push esi` as the **matrix** argument (`0x00468a30`, `0x00468aae`, `0x00468b20`).
- `0x004689b8` `fld [esi+0x24]`, `0x004689c1` `[esi+0x20]`, `0x004689cc` `[esi+0x28]`
  dotted with `0x006146fc`; `0x00468a36` `[esi+4]`, `0x00468a48` `[esi]`,
  `0x00468a4c` `[esi+8]` with the same. Read from the binary,
  `0x006146f0 = (1,0,0)`, `0x006146fc = (0,1,0)`, `0x00614708 = (0,0,1)`.
  So those are `at.y` (`[esi+0x24]`, word index 9) and `right.y` (`[esi+4]`, word
  index 1) of an `RwMatrix` — matching `AeroStabilize.cpp`'s `orient[9]` / `orient[1]`.

`0x40` is `sizeof(RwMatrix)`, which is the same stride A3's lead-2 fix corrected to.

### 4.6 The exe half is BLOCKED on an unported RenderWare function [UNCERTAIN U-9151]

The exe binding was **written, built, and measured** — it does not work, and the
reason is not a mistake in the binding.

`Vehicle_AeroStabilize(self, static_cast<float*>(xform), dt)` at
`VehicleControl.cpp:195` builds clean and then **crashes `mashed_re.exe` with exit
code `3221225477` = `0xC0000005` (ACCESS_VIOLATION) at ~3 s into the a8 solo recipe,
on 3 runs of 3** (`verify/d2_reopen_20260929/solo_a6bfix{1,2,3}/PROVENANCE.txt`; each
run ends `exe exited on its own rc 3221225477`, `NO motion_diag.log produced`).

Cause, read from the code path rather than inferred:

- A6b's entire effect is two `RwMatrixRotate(orient, axis, ang, 1)` calls
  (`AeroStabilize.cpp`) — combine mode **1**, `rwCOMBINEPRECONCAT`.
- `Math/RwMatrixRotateInner.cpp:169-176` resolves mode 1 (and 2) through the RW
  **device** table: it reads `*(uint32*)0x007d4028` and `*(uint32*)0x007d3ff8`, then
  calls the matrix-mult function pointer at `devBase + 8`.
- Those absolute addresses are mapped in the injected `.asi` and **not** in
  `mashed_re.exe`. That file's own header already says it:
  "Modes 1/2 are thus device-state dependent (live in the dev .asi; in the standalone
  they require RW device init — WS-E). Mode 0 ... is fully self-contained."

So with `orient` bound, the standalone's very first airborne A6b call dereferences
unmapped memory. Same RVA-tunnel class as the `kDegToRad` fix in
`Math/RwMatrixRotate.cpp` (2026-08-21) and the U-9138 device-slot rebind.

**Unblocker:** a standalone CPU port of `RwMatrixMultiply` `0x004c4600`, used as the
mode-1/2 fallback when the device table is unavailable — exactly the shape of the
U-9138 fix (`Rw_TransformPoints` -> `Math::RwV3dTransformVectorsCPU`). No such port
exists: `0x004c4600` appears in-tree only as a function pointer into the original
image (`HUD/FontCtx.cpp:42`, C1) and as a read-only Ghidra note
(`Collision/RwpSolverMath2.cpp:85`). Writing one is a new verbatim-x87 leaf port with
its own verification, deliberately **not** done here rather than guessed.

The binding is therefore **reverted to `nullptr`**, with the blocker recorded at the
call site instead of the old stale "until A8 binds it" comment.

## 11.1 `0x004c4600` is a dispatcher; the multiply is `0x005cb2a0`

From the anchored `original/MASHED.exe.unpatched`
(`re/tools/disasm_fn.py 0x004c4600 0x004c4680`, RETs at `0x004c463c` / `0x004c4654` /
`0x004c466e`), `RwMatrixMultiply` does no arithmetic at all:

```
0x004c4600  mov  ecx, [0x007d4028]     0x004c460c  mov  ebp, [0x007d3ff8]
0x004c461a  mov  eax, [ecx+ebp+4]      0x004c4622  and  eax, 0x20000      ; identity bit
0x004c4627  test ebx, eax / je         ; ebx = A->flags -> A identity: out = B
0x004c463d  test edi, eax / je         ; edi = B->flags -> B identity: out = A
0x004c465c  call [ecx+ebp+8]           ; THE DEVICE MULTIPLY, cdecl (out, A, B)
0x004c4663  and edi, ebx / mov [esi+0xc], edi   ; out->flags = A->flags & B->flags
```

Argument decode (balanced against the 5 prologue pushes): `arg1 = out`, `arg2 = A`,
`arg3 = B`; the `call` pushes B, A, out, so the device routine is `f(out, A, B)`.

**Which routine the pointer holds was MEASURED, not inferred.** New
`scenario_launch.py --peek` indirect form `i<rvaA>+<rvaB>+<off>` reads the u32 at each
of two RVAs, adds them and the offset, and reads that absolute address — exactly the
device-table pattern. On a running race (`--track 3 --mode 10 --cars 4 --car 0
--hold 20`), two samples 3.7 s apart, identical:

```
[0x007d4028] = 0x0000014c   [0x007d3ff8] = 0x02d28d80 (heap, per-run)
[devBase+0]  = 0x007d4004
[devBase+4]  = 0x00020000   <- the identity mask, matching the 0x20000 literal at 0x004c4622
[devBase+8]  = 0x005cb2a0   <- THE MULTIPLY
```

`0x005cb2a0` (RET `0x005cb402`) is a 4x3 row-vector matrix multiply that accumulates each
component on the x87 stack and rounds to f32 once, at the `fstp`.

## 11.2 The port, and why it is naked x87

`mashedmod/src/mashed_re/Math/RwMatrixMultiplyCpu.cpp`:

- `RwMatrixMultiplyCPU` — a **naked verbatim transcription** of `0x005cb2a0`, every
  instruction carrying its address. Not plain C++: with `/arch:SSE2` a C expression
  rounds at every operation, and the sibling stand-in
  `Math/RwV3dTransformPointsCPU.cpp` records what that costs ("9/10 bit-identical, the
  10th off by 1 ULP … a summation-order difference"). A matrix that is preconcatenated
  every airborne frame cannot carry a 1-ULP drift.
- `RwMatrixMultiplyCPUDispatch` — `0x004c4600`'s two identity short-circuits and its
  flags tail, for completeness. Not on the A6b path (`RwMatrixRotateInner` calls the
  device slot directly, as the original does).

`Math/RwMatrixRotateInner.cpp` mode 1/2 now takes `identWord` and `mul` from a variable
`s_forceCpuMul` rather than an `#ifdef`: 1 in `mashed_re.exe` (CPU), 0 in the `.asi`
(live device table, unchanged). It is a variable so the `.asi` can export the standalone
branch and **measure** it instead of arguing for it by composition.

## 17.3 ROOT CAUSE, with instructions: the last-contact damp is skipped

`0x0046ef70`'s tail applies a scalar damp to the velocity it just wrote. The port skips it.
Disassembly from the anchored `original/MASHED.exe.unpatched`
(`py -3.12 re/tools/disasm_fn.py 0x0046ef70 0x0046f6c0`):

```
0046f00d  lea esi,[edi+0x4b4]          ; ONCE, before the loop
0046f013  lea eax,[esi-0xc]            ; EAX = rec+0x4a8  = SLOT 0's base
0046f016  mov [esp+0x1c],eax           ; saved at [S+0x1c]
...
0046f522  mov eax,[esp+0x1c]           ; reloaded, ESP is back at S
0046f5ae  mov ecx,[eax+4]              ; = [rec+0x4ac] = SLOT 0's KEY
0046f5b1  cmp ecx,-2
0046f5b4  je  0x46f5f3                 ; skip the damp ONLY when slot 0's key == -2
0046f5b6  fld dword [esp+0x18]         ; local_74
0046f5ba  fmul dword [0x5cc31c]        ; * 3.0
0046f5c0  fcom dword [0x5cc9c8]        ; vs 0.9  -> clamp
0046f5d5..0046f5ed                     ; vel[0..2] *= fVar5
```

The port (`Collision/ContactFixup.cpp:245`) had

```cpp
if (pfVar7 && *(int*)((char*)pfVar7 - 8) != -1) { ...damp... }
```

which is wrong on **both** operands:

| | ORIGINAL | PORT (before) |
|---|---|---|
| pointer | `[esp+0x1c]` = `rec+0x4a8`, **slot 0**, loaded once at `0x0046f013` | `pfVar7`, the **last** slot the loop touched (slot 17) |
| field | `[eax+4]` = `rec+0x4ac` | `pfVar7-8` |
| sentinel | `!= -2` | `!= -1` |

Both errors push the same way. On the D2 scenario the reporting slots are 5 and 9, so slot 17's
key is `-1` and the port's guard is **false** -> no damp, ever. Slot 0's key is also `-1`, and
`-1 != -2`, so the **original's** guard is **true** -> the damp is applied.

**The ESP walk that settles `[esp+0x1c]`** (it matters, because the same displacement is used
for a float accumulator): with `S` = ESP after the three prologue pushes, every push in the body
is cleaned (`0x0046f1b9`+`0x0046f1ba`+`0x0046f1cd` -> `add esp,0xc` @`0x0046f1f0`;
`0x0046f2cd`+`0x0046f342` -> `add esp,8` @`0x0046f35a`; `0x0046f368`+`0x0046f36d` ->
`add esp,8` @`0x0046f379`; `0x0046f3d7` -> `add esp,4` @`0x0046f449`; `0x0046f48a` ->
`add esp,4` @`0x0046f4c6`), and `pop esi/ebp/ebx` + `add esp,0x80` @`0x0046f6b9` closes at
delta 0. So:

### HOT-PATH DISCIPLINE — this is the part that can go wrong

`0x004c3ac0` has **120 confirmed call sites image-wide** (`re/tools/callsites.py 0x004c3ac0`,
0 byte-pattern hits rejected). That is exactly the class CLAUDE.md warns about: `Interceptor`
on >1000 calls/s destabilises Mashed in ~6 s. Three mitigations, all in the probe:

1. **COUNT-FIRST.** `--mag-probe count` makes the callback body a single increment and reads
   no memory, so the RATE is measured before any run that reads vectors.
2. One object lookup on the hot path (`MP_SITES[returnAddress]`), then an immediate return.
3. **Hard row cap with AUTO-DETACH** (`--mag-probe-limit`), so exposure is bounded even if the
   rate is high.

### NEXT COMMAND, and it is not inside A6a

The quantity to explain is now specific and it has a threshold attached: **why does
`|cos(velocity, wall normal)|` FALL between the original's post-bounce contacts and RISE
between the port's?** Both sides leave the first bounce with nearly the same direction
(`0.7739` original, `0.7475` port — the port's is the *more* tangential of the two) and the
same nose (`fwd` `(-0.8596, 0.5110)` original against `(-0.869, 0.495)` port). What differs is
the TIME between contacts: 19 frames on the original against 1-2 on the port, so the original
gets an order of magnitude more free flight to rotate its velocity before the wall is asked
again. **That is a contact-CADENCE question, not a force question**, and it is the first
framing in this whole re-open that is neither inside A6a nor slip-coupled:

1. Instrument the port's inter-contact interval directly (it is already in
   `world_contact.log`'s ordinal plus `MASHED_SUBSTEP_VELPROBE`'s `c9ec`) and get the
   original's from `--fixup-probe`'s `frame` column: 23 fixups at frames 978, 997, 1010, 1022,
   1034, 1046, 1059, 1071, 1083, 1096, 1254, 1351, ... against the port's 211.
2. Then ask what re-arms the contact: `VehicleContactHistoryUpdate` `0x00470ae8` /
   `ContactHistoryLookup` `0x00468b40` and the 32-slot history at `veh+0xbfc`. §19 measured
   that the original's slot-0 history is all-zero on 22 live samples, i.e. it re-latches too —
   but "re-latches when re-penetrated" and "re-penetrates every frame" are different claims and
   only the first was tested.
3. The depth series is the cheap discriminator and is already captured: ORIGINAL
   `-0.02056, -0.00038, -0.00123, -0.00011, ...` against PORT
   `-0.0159, -0.0040, -0.0023, -0.0006, -0.0017, -0.0004, ...`. Both graze. So it is not
   penetration depth per contact; it is how often the hull returns to the plane.
