## Correction (2026-07-31, orchestrator iter17)

**The previous version of this plate was materially wrong and would have produced
a broken port.** It described the function as `int FUN_00482900(void)` — zero
arguments — with `FUN_004a2c48` as a "checkpoint/frame count getter". Both claims
are false, and they came from trusting the decompiler's signature over the
disassembly.

`FUN_004a2c48` is **`__ftol`**, the MSVC CRT x87 round-to-int64 helper
(`hooks.csv:254` — already C3, byte-identical, ported at
`mashedmod/src/mashed_re/Math/FPURound.cpp`). It takes its input **in ST0**, not
on the stack. Ghidra cannot see x87 register arguments, so it renders the call as
`FUN_004a2c48()` and, because the function's own two arguments are consumed only
by x87 instructions, it reported the whole function as `void`-parameter.

The arithmetic conclusion of the old plate (`count * 36 + 412`) happens to be
correct. Its derivation was not: the count is **computed from two arguments**,
not fetched from anywhere.

## Mechanical description (confirmed from disassembly)

`int FUN_00482900(float param_1, int param_2)` — TWO arguments.

    frames = (int)(param_1 * 60.0f / param_2);   // via __ftol
    size   = frames * 0x24 + 0x19c;
    FUN_004987b0("Replay size is %d\n", size);
    return size;

Disassembly, 0x00482900..0x0048292f (47 bytes):

    0x00482900  D9 44 24 04         FLD   float ptr [ESP+4]      ; param_1 (FLOAT)
    0x00482904  56                  PUSH  ESI
    0x00482905  D8 0D 28 C7 5C 00   FMUL  float ptr [0x005cc728] ; * 60.0f
    0x0048290B  DA 74 24 0C         FIDIV dword ptr [ESP+0xc]    ; / param_2 (INT)
    0x0048290F  E8 34 03 02 00      CALL  0x004a2c48             ; __ftol: ST0 -> EAX
    0x00482914  8D 34 C0            LEA   ESI,[EAX+EAX*8]        ; EAX*9
    0x00482917  8D 34 B5 9C 01 00 00 LEA  ESI,[ESI*4+0x19c]      ; *4 +412 => EAX*36+412
    0x0048291E  56                  PUSH  ESI
    0x0048291F  68 4C F2 5C 00      PUSH  0x5cf24c               ; "Replay size is %d\n"
    0x00482924  E8 87 5E 01 00      CALL  0x004987b0             ; logger
    0x00482929  83 C4 08            ADD   ESP,8                  ; __cdecl cleanup
    0x0048292C  8B C6               MOV   EAX,ESI
    0x0048292E  5E                  POP   ESI
    0x0048292F  C3                  RET

Note `FIDIV dword ptr [ESP+0xc]`: the `PUSH ESI` at 0x00482904 has already moved
ESP down 4, so `[ESP+0xc]` is the original `[ESP+8]` — the SECOND argument. It is
an **integer** divisor (`FIDIV`, not `FDIV`).

The `*36` is done as `LEA ESI,[EAX+EAX*8]` then `LEA ESI,[ESI*4+0x19c]`, i.e.
`(EAX*9)*4 + 412` — a strength-reduced multiply, not a literal `imul 36`.

## Uncertainties

- The meaning of `param_1` and `param_2` is **not** established here. The
  arithmetic `param_1 * 60.0f / param_2` is consistent with a seconds-to-frames
  conversion at 60 fps with `param_2` as a divisor, but nothing in this function
  names either, so no semantic is assigned. [UNCERTAIN U-9033] — resolve from the three
  call sites, not from this body.
- The 60.0f is a raw constant here; this function does not read a frame-rate
  global, so it is **not** evidence about the engine's tick rate.
