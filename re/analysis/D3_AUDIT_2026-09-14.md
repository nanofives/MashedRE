### 1.2 What DOES drive the opponents

`D3d9Render/TrackRenderer.cpp:2831-2960`, labelled in-source as **"Option B (2026-06-30)"**. Per
opponent slot, per frame:

1. `Ai::Ai_ComputeTarget(v, a.pos[0], a.pos[2], &tx, &tz)` (`TrackRenderer.cpp:2877`) →
   `AiStandalone.cpp:1299`, which is **ported**: `SelectSpline(v)` (FUN_00418560's bank pick) +
   `SplineLookahead(...)` (FUN_00443dc0 phases 1-8). This is the only ported AI code on the live path.
2. A **hand-written turn-rate + velocity-shaped-speed motion model** consumes that target. The
   source says so at `TrackRenderer.cpp:2832-2836`:
   > *"opponents drive the FAITHFUL racing-line target … with a robust turn-rate + velocity-shaped-speed
   > motion model … This races the real line **without the verbatim ControlStep bands'** accel+brake
   > deadlock against the approximate physics chain."*
3. Scaffold-only behaviours layered on top, with no original counterpart cited:
   an **anti-stuck marshal recovery** that teleports a stalled car +2 gates
   (`TrackRenderer.cpp:2852-2862`), and `a.spin` / `a.slow` timers (`:2846-2850`).

**Conclusion (AI):** the AI's *where to go* is ported; the AI's *how to drive* and the entire
per-frame tick spine are scaffold. The D3 gate for opponents is a **port + wire task**, not a
flag inversion.

## 2. Powerups (WS-D) — MEASURED

### 2.1 The ported dispatcher does run, under a synthetic invocation

Confirmed present and wired: `PowerupBackendImpl` (`TrackRenderer.cpp:3070`), bound once via
`EnsurePowerupBackend()` (`:3221-3223`, `pw_.Init(pu_be_)`).

Every call into the ported system is inside **one function**, `TrackRenderer::PowerupFireOnce`
(`TrackRenderer.cpp:3244-3252`). A tree-wide search for `pw_.` returns exactly six lines — the
`Init` at `:3222` and five inside `PowerupFireOnce`:

```
3247  pw_.Activate(code);
3248  pw_.SetFireButtons(true,  false); pw_.Tick(0.016f, pu_player_, 6);   // primary
3249  if (pw_.Armed()) { pw_.SetFireButtons(false, true); pw_.Tick(...); } // secondary
3250  pw_.SetFireButtons(false, false);
3251  pw_.Deactivate();
```

The source states the mismatch itself (`TrackRenderer.cpp:3239-3243`):
> *"The original is a per-frame fire-button loop; the standalone fires one pickup per key press, so
> we pulse primary (mode 2) then secondary (mode 1) … then deactivate (one use per collected pickup)."*

**Two structural gaps follow, neither flag-selected:**

- **G-D1 — no per-frame dispatcher tick.** The original **FUN_0045bba0** is a per-frame 3-pass loop
  over the slot array (`0x0088fbe0`, stride `0xb4`). Standalone runs it as a 1-2 frame burst per key
  press. Any decision that needs multi-frame state cannot be exercised: the cooldown countdown, the
  charge state machine, and the RFlame jet transitions (the `charge/jet` decisions the port describes
  as verbatim in `Powerup/PowerupSystem.h:15-17`) are entered and torn down within two synthetic ticks.
- **G-D2 — opponents never fire.** `PowerupFireOnce` is reached only from `FireHeldPowerup()`
  (`:3253`, player key press) and `FirePowerupKind()` (`:3265`, demo/testing). No path exists for
  slots 1..3. `SyncHostCar()` (`:3225`) populates `pu_ai_[]` so effects can *target* AI cars, but no
  AI car is ever an *owner*.

### 2.2 Leaves

Unchanged from `re/analysis/structs/powerup_system.md` §8-9 and re-confirmed here: every leaf goes
through `IPowerupBackend` (`Powerup/PowerupSystem.h:70+`) and is realised by `PowerupBackendImpl` as
a **standalone reimplementation on renderer-side visuals** (`TrackRenderer.cpp:3173-3183` per-type
particle burst; missiles integrated by `UpdatePowerups` at `:3277+` with a `hitR = R*0.05f`
proximity hit and a `SpinOut()` result). These are not ports of the original leaves
(pools `DAT_006883bc` stride `0x6c` / `DAT_00684ea8` stride `0x110`, FX FUN_00465e80 / FUN_00465ca0,
contacts FUN_004b4cd0). That is by design per the kickoff; recorded, not a regression.

### 2.3 Powerup flag classification

`Powerup/` contains **zero** `getenv` calls. The only related flag is
`MASHED_NO_PICKUPS` (`TrackRenderer.cpp:5264`) — **dev-override**, separates orb billboards from the
particle pass for render profiling. Orb economy is the `PickupField` scaffold, data-faithful to the
9 codes.

### 2.4 Stale string found (powerups)

- `Race/RaceSession.cpp:87` — `"… orb collect/respawn; effects TODO"`, and the file header at
  `RaceSession.cpp:79` — *"Only Powerups remains a genuine TODO stub."* Both stale: the ported
  dispatcher + the 9 decision functions **are** wired (`:3244`), with the two gaps in §2.1.

## 6. Corrections to this audit (added 2026-09-14, after the step-2 measurement)

Recorded here rather than edited in place, so the audit keeps its measured/refuted shape.
Full detail: `re/analysis/D3_AI_TICK_WIRING_2026-09-14.md`.

1. **§1.3 `MASHED_AI_PUREPURSUIT` — my "dead in the exe" row was right, but for a reason
   that has since changed, and the in-source comment I read it against was inverted.** The
   lambda at `AiStandalone.cpp:437-443` is `return (e && e[0] != '0')` — **OPT-IN, default
   OFF** — so the **verbatim bands are the default path** inside `ControlStep`, not the
   pure-pursuit shim. The comment above it claimed `=0` reverts to the bands, the exact
   inverse; fixed in-source this session. Polarity is correct for D3: the flag turns a
   ported behaviour OFF.
2. **§1.3 `MASHED_AI_PUREPURSUIT` / `STEERFLIP` / `NAV` are no longer dead** once
   `MASHED_AI_TICK=1` is set, since `ControlStep` is then reachable. `STEERFLIP` affects
   only the opt-in shim and stays inert on the default path.
3. **§1.1 understated the defect.** The tick was not merely uncalled: `g_aib.pos/.vel/.alive`
   were never written either, so `aib_own_xz` returned (0,0) and `aib_alive` returned 0 for
   every car. The tick would have been **inert even if called** — WS-AI-BRIDGE part (2) was
   half-landed, not landed.
4. **New, outside the audit's static scope:** every `scenario_launch.py` race leaves the AI
   output-slot table at zeros, so all four cars write controller 0's ctrl block. Measured
   `[0,0,0,0]`; blocks 1-3 all-zero for 2710 frames. Fixed by `--poke-ctrl-slots`. Any prior
   AI-behavioural observation taken through that launcher is suspect; the A8/D2 physics
   captures are not affected (they drive block 0 directly).
5. **§4 worklist item 1 is now specific.** The AI gap is not "wire the tick" — the tick is
   wired and runs. It is **`FUN_00443300` and the `FUN_00443dc0` curvature-walk/wall-march
   tail**, whose absence puts the bearing error into the bands' full-steer range. Measured:
   standalone steer has 2-3 distinct commands per car against the original's 33-96.
