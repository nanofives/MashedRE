## 1. The instrument — `scenario_launch.py --statediff-puhook`

Hooks (all Interceptor.attach, ~60 calls/s, far below the 1000/s limit):
`FUN_0045bba0` (the dispatcher, sole caller `0x0040fcd0`), the 9 FIRE entries, the 8
distinct CANFIRE entries and `FUN_0045bac0` (deactivate; the return address says which
branch deactivated). One row per dispatcher call per slot that holds a power-up or had
an event, written to `<out>.puhook.csv`: `frame,call,state,slot,ctrl,cur3,prev3,cur4,
prev4,boxstate,dt,act,code_pre,h_pre,code_post,h_post,fire_modes,canfire_rets,deact_ra,
rec_pre,rec_post`. `rec_*` is the ARM handle's pool record in hex. `dt` is the exact float
bits of `DAT_007f100c`.

`--pu-plan 19,18,...` drives slot `--pu-subj` (default 0, the player). It is **CONTRIVED
state (C3-grade)**, same class as `--poke-ctrl-slots`: each type is activated through the
original's own `FUN_0045c010(slot, code)` from the dispatcher's onEnter (game thread), and
the ctrl byte the dispatcher reads is written each frame from a fixed pattern (press 1 /
2 / 6 / 30 / 1 / 1 / 2 / 60 frames with gaps). Everything downstream is the original.
After the pattern, a still-armed type is discarded through the original's own discard
branch (§2.3).

Recipe (the cited runs, muted, `--poke-ctrl-slots`, PIDs killed by the launcher only):

```
py -3.12 re/frida/scenario_launch.py --track 0 --mode 10 --cars 4 --car 0 --poke-ctrl-slots \
   --statediff-out verify/d3_pu_20260926/o3.msd --statediff-car 0 --statediff-drive \
   --statediff-puhook --pu-plan 19,18,9,17,11 --pu-warm 60 --hold 45
# o4: same with --pu-plan 7,10,12,16
```

Two runs are needed because state 6 (below) lasts ~600-750 dispatcher calls on Training
before the race sub-state leaves 6 (`o1`: 6 from call 861 to 1604, then 7).

`re/tools/pu_trace.py <csv>` prints a compact per-activation trace (changed record dwords
per frame). Traces are committed next to each capture (`o*.trace.txt`).

## 2. MEASURED — byte-level facts about the dispatcher

### 2.1 The fire mode is ONE button's current and previous frame, not two buttons

`0x0045bd72` reads `[0x007f103f + ctrl*0x4c]` and `0x0045bd84` reads
`[0x007f14ff + ctrl*0x4c]`. The cook `FUN_00496530` copies each player's 0x4c-byte block
`0x007f1038+p*0x4c` to `0x007f14f8+p*0x4c` with `REP MOVSD` (`ECX=0x13`, `0x0049654d..
0x00496552`) and then zeroes the block (`0x00496563..0x00496568`) before rewriting it.
So `0x007f14ff` is last frame's `0x007f103f`. The lattice at `0x0045bd72..0x0045bdaa`:
press edge → 2, held → 3, release edge → 1. The port's comment called these "primary"
and "secondary"; the decode itself was the same lattice, so only the input meaning
changes. Measured non-degenerately: every `prev3` in `o3`/`o4` equals the port's
cook-shadow latch (§3, `prev3` column checked on every row).

### 2.2 The per-slot pass runs only when `DAT_0063ba8c == 6`

`FUN_0040e350` is `MOV EAX,[0x0063ba8c]; RET` (`0x0040e350`). The dispatcher compares it
with 6 at `0x0045bc2b` and skips the whole per-slot pass otherwise. `DAT_0063ba8c` is a race
sub-state written with immediates 1..11 at `0x0040d3e7..0x004111a6` (6 at `0x004104e3`).
The per-type TICK pass (`0x0045bdf2`) still runs in every state.

### 2.3 A discard branch the port did not have

Neither fire byte set and `[0x007f1040+ctrl*0x4c]` set with `[0x007f1500+ctrl*0x4c]`
clear (block `+8` press edge) → `FUN_0045bac0` at `0x0045be4d`. Measured: GUN in `o1`/`o3`
ended through it (return address `0x45be52`). Now ported (`PowerupSystem.cpp`, Tick).

### 2.4 The activation type is the SECOND stack argument (corrects U-WSD-3 addendum)

`FUN_0045c010(idx, code)` converts `idx` to `0x0088fbe0 + idx*0xb4` (`0x0045c014`,
`0x0045c01a`) and jumps to `FUN_0045bfa0`, which does `PUSH ESI; MOV ESI,[ESP+0xc]`
(`0x0045bfa0..0x0045bfa1`) — the second argument — before the lookup. The
`powerup_system.md` addendum of 2026-07-06 called the pushed `0x10` "unread"; it is the
type. So the dispatcher's own unarmed branch (`0x0045bd40..0x0045bd47`,
`FUN_0045c010(slot, 0x10)`) always arms code 16 = R_FLAME, and the box-collect caller
`0x00458a1b` passes `[EDI+0x24]` (the box record's type). This is how the capture
activates types.

## 4. MEASURED — the AI fire byte, and opponents in the original

- `FUN_00415220` writes `MOV BYTE [EDI+7],1` at `0x0041536c` (and 7 more sites through
  `0x00415793`). `FUN_00418560` zeroes `[EDI+7]` at `0x00418588` with block
  `EDI = 0x007f1038 + slot*0x4c`. The dispatcher reads `0x007f103f` = block `+7`. So `[7]`
  is the power-up fire byte. `AiState.h` said "[3] fire, [6],[7] zeroed scratch";
  corrected in place. `[3]` is left `[UNCERTAIN]`: no power-up reader of `+3` was found.
  Consequence for the D3 AI capture: the `c3` column of `--statediff-aistep` is not the
  fire byte.
- In the original, opponents own and fire: `o1` slot 2 held P_MINE and fired (mode 2 at
  call 1027, mode 1 at 1028, mode 2 at 1057, CANFIRE deactivate at 1058), and slot 1's
  OIL was dropped through the box state-2 branch (return address `0x45bc9d`, call 1362).

## 5. PORTED — G-D1 and the G-D2 structure

- `PowerupSystem` holds 4 slots. `Tick(dt, cars[4], raceState)` is the dispatcher:
  per-slot CANFIRE → deactivate, fire mode from `SetInput`'s cook-shadow latch → FIRE,
  the discard branch, then the per-type TICK pass for every slot.
- `TrackRenderer::TickPowerupDispatch` calls it every `UpdateCar` frame
  (`PowerupFireOnce`, the 1-2 frame burst, is deleted). Slot 0 = the player, armed from
  the pickup field's held orb, input = the fire key's HELD state (`exe_main.cpp`,
  `SetPowerupFire`). Slots 1..3 = the AI cars, armed by `PickupField::CollectAt`, input =
  their ctrl block `[7]`/`[8]` (identity slot→ctrl, as the allocator commits at
  `0x0043f895`).
- Live evidence (`mashed_re.exe`, `MASHED_DRIVE_DEMO=1`, Training):
  `verify/d3_pu_20260926/sa_run.csv` — 330 dispatcher ticks on 330 consecutive frames
  (50..379), modes 2, 3 and 1 all passed to FIRE. `sa_long.csv` — 2391 consecutive.
