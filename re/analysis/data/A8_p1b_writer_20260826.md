# A8 — the writer of per-wheel field `p[0x1b]` (record+0x210)

Ghidra pool slot `Mashed_pool0`, read-only, MASHED.exe image base 0x00400000.
NO-GUESSING: every claim below cites the exact RVA/address it came from.

Addressing recap (given, re-confirmed here):
- vehicle record base `DAT_008815a0`, stride 0xd04.
- Wheel-0 block spans roughly record `+0x16c .. +0x230` (0xc4 stride). The same
  block is addressed from three different base offsets in the physics code:
  `+0x16c` (int*, `unaff_EDI+0x5b`), `+0x1a4` (int*, A6a `piVar12`), and `+0x1f4`
  (float*, A5 `pfVar14`/`ESI`). All resolve to the same bytes.
- `p[0x1b]` = record `+0x210` (w0), `+0x2d4` (w1), `+0x398` (w2), `+0x45c` (w3).
- In A5's frame `ESI = record+0x1f4`, so `p[0x1b]` = `[ESI+0x1c]`,
  `p[0x1a]` = `[ESI+0x18]` = record+0x20c, `p[0x18]` = `[ESI+0x10]` = record+0x204.

## Q1 — THE WRITER(S) of `p[0x1b]` (record+0x210 / +0x2d4 / +0x398 / +0x45c)

**Exactly one write site, in `FUN_0046ddb0` (A5), inside its tail per-wheel loop**
(loop head `0x0046e761`, wheel stride `ADD ESI,0xc4` at `0x0046e981`, 4 iterations
via the counter set to 4 at `0x0046e757`). ESI = record+0x1f4 (`LEA ESI,[EDI+0x1f4]`
at `0x0046e751`).

Store instructions:
```
0x0046e86c  FLD  float ptr [ESI+0x18]      ; ST0 = p[0x1a]  (record+0x20c)
0x0046e86f  FMUL float ptr [ESI+0x10]      ; ST0 = p[0x1a] * p[0x18]  (p[0x18]=record+0x204)
0x0046e872  FST  float ptr [ESI+0x1c]      ; *** WRITE p[0x1b] = p[0x1a] * p[0x18] ***
0x0046e875  FCOMP float ptr [0x005d757c]   ; compare product vs DAT_005d757c (= 0.0)
0x0046e87b  FNSTSW AX
0x0046e87d  TEST AH,0x5
0x0046e880  JP   0x0046e885
0x0046e882  MOV  dword ptr [ESI+0x1c],EBP  ; *** clamp: if product < 0.0, p[0x1b] = 0 (EBP=0) ***
```

So the full stored expression is:
```
p[0x1b] = max( p[0x1a] * p[0x18], 0.0 )      // clamp-to-zero, not clamp-to-abs
```
Decompiler rendering (FUN_0046ddb0): `pfVar14[7] = pfVar14[6] * pfVar14[4];
if (pfVar14[6]*pfVar14[4] < DAT_005d757c) pfVar14[7] = 0.0;`

No other writer exists. Image-wide `search_instructions` for the literal displaced
forms of the other three wheels (`+0x2d4`, `+0x398`, `+0x45c`) returns only
ESP-relative locals and unrelated structs — the wheel field is never written by a
literal `record+offset`; the single base+index loop above covers all four wheels.
When the wheel is inactive (`[ESI-0x5c]==0`, JZ at `0x0046e764` → `0x0046e970`),
only `+0x20/+0x24/+0x28` are zeroed; `p[0x1b]` (+0x1c) is left at its prior value.

## Q2 — LIVE per frame vs setup-only

The writer is in **A5 = FUN_0046ddb0**, which A4 (`FUN_00470670`) calls once per
frame (dispatcher step 3), before A6a (`FUN_00467650`). Order within the frame:
`A4 → A5(writes p[0x1b]) → A6a(reads p[0x1b])`. The substep loop `FUN_004709a0`
never calls A4/A5/A6a, so `p[0x1b]` is written exactly once per render frame, per
wheel, and consumed the same frame in A6a. **This writer is LIVE, not setup.**

## Q3 — WHAT IS THE FIELD (mechanical)

`p[0x1b] = max(p[0x1a] * p[0x18], 0)`. Since `p[0x18]` is a constant = **1.0** for
every wheel (see Q4), mechanically `p[0x1b] == max(p[0x1a], 0)`, i.e. it is a
floored copy of `p[0x1a]`. And `p[0x1a]` (record+0x20c) is written per-wheel
**earlier in the same function A5** (middle section, the four unrolled blocks writing
`unaff_EDI[0x83/0xb4/0xe5/0x116]`), gated by `if ((float)EDI[0x278] != 0.0)`
(0x278 = record+0x9e0 = grounded-wheel count, accumulated +1.0 per grounded wheel in
A5's first loop). The exact wheel-0 arithmetic (disasm 0x0046e3f6–0x0046e473):
```
fVar4 = (EDI[0x50] / EDI[0x9e0]) * _DAT_0088e610          ; 0x46e3f6 FLD [EDI+0x50] /
                                                          ;   FDIV [EDI+0x9e0] / FMUL [0088e610]
fVar5 = fVar4 * _DAT_005ccac8   (= fVar4 * 0.3333)        ; 0x46e409  (clamp bound)
fVar6 = (EDI[0x180]*vΔx + EDI[0x184]*vΔy + EDI[0x188]*vΔz) * _DAT_005ce018   ; 0x46e419-0x46e43b
fVar6 = clamp(fVar6, -fVar5, +fVar5)                     ; 0x46e441-0x46e46d
p[0x1a] = fVar4 + fVar6                                   ; 0x46e46d FLD [ESP+0x14]/FADD/
                                                          ;   0x46e473 FSTP [EDI+0x20c]
```
(the per-wheel `EDI[0x180/0x184/0x188]` become `[0x91/0x93]`, `[0xc2..]`, `[0xf3..]`
for wheels 1-3.) Because the clamp is `±fVar4/3`, `p[0x1a] ∈ [fVar4·2/3, fVar4·4/3]`,
so its magnitude is set by `fVar4` and the front/rear spread is at most 2:1
(`(4/3)/(2/3)`), matching the measured 1091/536 ≈ 2.04.

I do NOT assign a semantic name; mechanically it is "(vehicle scalar record+0x50 ÷
grounded-wheel count) × global _DAT_0088e610, plus a ±1/3 velocity-projection term,
floored at 0."

## Q4 — THE SCALE (candidate for our 26-40x-small port)

The magnitude of `p[0x1b]` is dominated by `fVar4 = (EDI[0x50] / grounded_count) *
_DAT_0088e610` (the clamped `fVar6` only spreads ±1/3 around it). Walking every
factor:

- **REFUTED: `_DAT_0088e610`** (0x0088e610). It reads `00000000` statically (runtime-
  init) — but its initializer `FUN_00470c70` (body 0x00470c70–0x00471423; the store
  is `FSTP [0x0088e610]` at 0x00470f28) computes
  `_DAT_0088e610 = (*[ESP+0x3c]) * _DAT_005cea80` and immediately
  `_DAT_0088e5f0 = _DAT_005ccd08 / _DAT_0088e610`. So `_DAT_0088e5f0 * _DAT_0088e610 =
  _DAT_005ccd08 = 3000.0` (a .rodata constant). The two globals are **reciprocals
  through a fixed constant**: since the port already matches `_DAT_0088e5f0`
  (suspScale), `_DAT_0088e610` is necessarily correct too. This is NOT the bug.

- **REFUTED: `p[0x18]`** (record+0x204). Vehicle-init `FUN_0046b540` sets it to
  `0x3f800000 = 1.0` for all four wheels (`0x0046bb30` w0, then +0x2c8/+0x38c/+0x450),
  and no per-frame code writes it. (The `+0x204` writers `0x0047a060`/`0x0047acb0`
  belong to the course/BSP struct in `FUN_0047a020` "CourseDescInit", a *different*
  object — same offset, unrelated.) p[0x18] = 1.0 in original and, if the port inits
  the record the same way, in the port too — so it contributes no scale.

- **PRIME CANDIDATE: `record+0x50`** (decompiler `unaff_EDI[0x14]`, read as
  `FLD [EDI+0x50]` at 0x0046e3f6) — the per-vehicle scalar in `fVar4`'s numerator.
  It is the ONLY magnitude input to `fVar4` that the user has not verified. If the
  port's vehicle record has `+0x50` too small (by ~26-40×), `fVar4`, its clamp bound
  `fVar5`, and hence all of `p[0x1a]`/`p[0x1b]` shrink by the same factor while the
  ±1/3 front/rear spread (and thus the SHAPE) is preserved — exactly the symptom.
  ACTION FOR THE PORT: compare `record+0x50` original-vs-standalone in the statediff
  capture; find where the port fills `+0x50` (a vehicle mass/inertia-group field at
  +0x50/+0x54/+0x58/+0x5c) and check the units/source.

- **SECONDARY: grounded-wheel count `record+0x9e0`** (`EDI[0x278]`, the divisor). It
  is 1.0–4.0, so it cannot by itself account for 26-40×, but if the port leaves it at
  a wrong constant it perturbs `fVar4`. Lower priority.

- `_DAT_005ccac8` = 0.3333, `_DAT_005ce018` = 0.002 — .rodata scalars affecting only
  the ±1/3 `fVar6` spread, not the uniform magnitude; verify but unlikely.

Note the measured shrink is 26.5× front / 40.6× rear (ratio 41.2/13.2 = 3.12 vs
original 2.04), i.e. not perfectly uniform. A pure `record+0x50` error keeps the ratio
at 2.0 exactly, so the residual front-vs-rear drift (2.04→3.12) is a *second, smaller*
effect on top — most plausibly the `fVar6` velocity-projection term
(`EDI[0x180..0x188]` wheel direction vectors, or `_DAT_005ce018`) reading slightly
differently. Fix `record+0x50` first (accounts for the bulk 26-40×), then re-measure.

## Q5 — OTHER consumers of `p[0x1b]` (unit constraints)

All reads of `p[0x1b]` are in **A6a = FUN_00467650**, three sites (each `(float)
piVar12[0x1b]`, i.e. read as int→float — note the field is FST-stored as float by the
writer; the `(int*)` cast is a decompiler typing artifact, the bytes are a float):
1. `local_bc = piVar12[0x15]*piVar12[0x1b]*_DAT_0088e5f0*local_e4*_DAT_005cea0c;`
   (the `p[0x15]*p[0x1b]*suspScale*le4*0.0009766` term).
2. `local_98 = piVar12[0x16]*piVar12[0x1b]*_DAT_0088e5f0;`
   (the `p[0x16]*p[0x1b]*suspScale` inner arm).
3. `fVar4 = piVar12[0x1b]*_DAT_005cc31c*_DAT_0088e5f0*(float)local_94*_DAT_005cea08*
   _DAT_005ccabc;` (the `local_94 & 0x100 != 0` arm).
No consumer outside A6a. There is no second consumer at a scale we already match, so
Q5 does not independently pin the units — the only cross-check is the A6a force whose
other inputs already match, which is what localised the discrepancy to `p[0x1b]`.
