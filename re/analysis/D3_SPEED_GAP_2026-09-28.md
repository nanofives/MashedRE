### 1.2 The chain to bisect, and where each link is measurable

```
  AI ctrl bytes                 cook / descriptor              ported physics
  ctrl[0],[1] steer             (standalone: none —            VehiclePhysics_StepCar
  ctrl[4] accel                  blk[0..7] -> io.input[k],     (D2, RWP-3.7)
  ctrl[5] brake                  raw_steer = 1)                   |
      ^                                                           v
      |                                                       rec+0x9e4  (speed)
      +-------------------- read back by the NEXT AI step ---------+
```

- **Link 1 output** is observable on BOTH sides, call-for-call, in the `*.aistep.csv`
  already committed (`c0,c1,c3,c4,c5`). Original: `re/frida/scenario_launch.py
  --statediff-aistep`. Standalone: `MASHED_AI_STEPDUMP`.
- **Link 2** in the standalone is a straight copy — `TrackRenderer.cpp:2944`
  `for (int k = 0; k < 8; ++k) io.input[k] = blk[k];` with `io.steer = 0`,
  `io.raw_steer = 1`. The only modifier is the shock power-up (`io.input[4] *= 0.35f`,
  `TrackRenderer.cpp:2946`). So on the standalone side link 2 is testable by inspection
  plus an `a.slow` check; on the original side the descriptor write set is recorded in
  every provenance JSON (`descriptor_writes`: `block_base 0x007f1038`, `accel_byte 4`,
  `steer_bytes [0,1]`).
- **Link 3 output** is `rec_9e4`, which the standalone AI reads back through
  `aib_veh_f32` → `Vehicle::VehiclePhysics_RecordF32(v, 0x9e4)`
  (`TrackRenderer.cpp:100`). So the AI's *input* speed IS the ported physics' output.
  **The loop is closed**: a physics speed error feeds straight back into the steer bytes.

**Why that matters for the (b) question.** The steer magnitude at `0x00416648..0x00416656`
is literally

```
m = err * speed * 0.0030034          (_DAT_005cd0e8)
m = m * (curv * 0.05)                 when mode == 0 && curv > 20   (0x0041665c..0x00416679)
m = min(m, 255.0)                     (_DAT_005cd04c, 0x0041667b..0x0041668a)
ctrl[0] = RoundST0(m)                 (0x00416697)        [err < 180 branch]
ctrl[1] = RoundST0(m)                 (0x004167b1)        [err > 180 branch, err -> 360-err]
```

`speed` is `rec+0x9e4` read at `0x0041624c`-region via `FUN_0046d6d0` into local `[+0x1c]`.
So **`c0` and `c1` are proportional to the speed the physics reports**, up to the 255
clamp. A 17% speed error is a 17% steer-byte error by construction, and the launch
deficit (705 vs ~1900) is a 2.7x steer-byte error for the first 61 calls. Car 1's two
failing bands are exactly `c0_distinct` and `c1_distinct`. That is the hypothesis this
session tests — **tests**, not assumes.

### 1.4 The counterfactual, and the decision rule — fixed IN ADVANCE

No build is available, so "does fixing speed fix car 1" is answered by **offline
substitution**, not by a rebuild. Method:

1. **Reconstruct `err` exactly** for every window call, on both sides, from the columns
   already in the CSVs. `0x004165cc` writes `[0x008032d8 + v*0x14] = 360` and `0x004165f7`
   writes `[0x008032dc + v*0x14] = err` on the `err < 180` branch; `0x004166db` writes
   `[0x008032dc + ...] = 0` and `0x0041670c` writes `[0x008032d8 + ...] = err` on the
   `err > 180` branch. `RecordStepLocals` (and the original-side probe at `0x004165a5`)
   sample `hist_d8`/`hist_dc` BEFORE those writes, so call *n*'s `err` is recoverable from
   call *n+1*'s pair for the same `v`:
   `hist_d8 == 360` → call *n* took the low branch, `err = hist_dc`;
   `hist_dc == 0` → call *n* took the high branch, `err = hist_d8`.
2. **VALIDATION GATE (mandatory, before any counterfactual number is quoted).** Recompute
   `c0`/`c1` from the reconstructed `err`, the CSV's `curv`, and the CSV's own `rec_9e4`,
   using the formula in §1.2 verbatim, and compare against the observed `c0`/`c1`.
   **Require exact agreement on >= 95% of window calls.** If the gate fails, no
   counterfactual is reported; the section is marked `[UNCERTAIN]` with the next command.
   (Rationale: memory `arm-coverage-counters-before-first-run` and
   `schedule-derived-counts-are-not-evidence` — a model that cannot reproduce the observed
   bytes cannot be trusted to predict counterfactual ones.)
3. **Substitute speed only.** Replace `rec_9e4` at window index *i* with the original's
   speed at the same window index *i* (median over the 8 non-flip original runs, same car),
   change **nothing else** (same `err`, same `curv`, same branch, same clamp), recompute
   `c0`/`c1`, and re-score all 10 bands.

**DECISION RULE, fixed here:**

- **"Speed explains car 1"** — all three of car 1's currently-failing bands land inside
  the pure-regime-0 `K = 220` envelope of §10.3 after the substitution:
  `c0_distinct` ∈ 13..35, `c1_distinct` ∈ 21..70, `abs_steer_median` ∈ 7..23,
  **and** no band that currently passes is pushed out.
- **"Speed does NOT explain car 1"** — at least one of the three is still outside, or the
  substitution moves a band the wrong way.
- **"Partial"** — some of the three enter and some do not. Report per band, name the
  residue, and do **not** round it up to "explains".

The counterfactual is a bound on what a speed fix can buy, not a promise: it holds `err`
fixed, whereas in the live loop a changed speed changes the trajectory and therefore
`err` on the next call. **That limitation is stated here, in advance, and is repeated
wherever the result is quoted.** It makes the counterfactual a *necessary* condition test:
if the three bands do NOT come inside even with the original's exact speed trace
substituted, a speed fix cannot close (b) for car 1 — which is a sound refutation. The
converse (they do come inside) is suggestive, not proof, and will be labelled as such.
